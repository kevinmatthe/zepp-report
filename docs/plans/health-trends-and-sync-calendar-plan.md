# Zepp Report 趋势分析与同步日历改版计划

日期：2026-09-28。状态：方案待评审，本次只规划。

用户已确认：首页以总体趋势为主，同时提供“典型一天 + 指定日期叠加”。步数、活动时长和运动类型属于主要分析维度。此前要求的手动回溯与可恢复能力必须延续。

## 1. 目标和现状

目标是让用户先回答“这段时间发生了什么变化、与过去相比怎样、哪些天需要进一步看”，然后下钻具体日的心率、睡眠与活动。同步管理则直接回答“哪些日期已检查、哪些尚缺、哪里正在执行”。

代码核查发现：

- 当前页面使用两个原生日期输入，仅有近 7 天快捷按钮。
- `/api/data` 返回整个范围的逐日明细；默认直接把全部心率点连成长图，活动主要是表格。
- `/api/status` 只返回任务总数和最近 30 条，无法呈现完整年份的覆盖情况。
- `tasks` 记录日期 × 接口的最新状态；`records` 有原始粒度的规范化数据，`raw_versions` 有原始响应。任务成功允许返回空数据，因此“任务完成”不代表“有健康测量”。
- 现有归档结构足以重算新统计和部分活动类型，不应为 UI 改版重新向 Zepp 全量取数。
- 当前规范化过程丢弃了活动片段、走路/跑步时长等已有源字段，需要从原始归档补解析。
- 现有 `sleep_minutes` 是睡眠记录起止跨度，可能包含清醒段；不能直接重命名为实际睡眠时长。
- 本次只读核查时，归档范围为 30 天，任务状态共 180 项完成。全年/同比功能必须能处理未回填和历史不足。

## 2. 推荐路线与备选

推荐：保留 FastAPI、SQLite 和可靠同步链路，将前端拆为模块，增加本地打包的日期选择器和图表库。首选验证 Flatpickr 范围选择 + ECharts；在交互原型中验收移动端、键盘和年份快速跳转后锁定版本。组件不能满足交互要求则替换适配器，不影响业务 API。

备选一：继续完全手写 SVG 与日历，依赖少，但范围选择、缩放、分位带、点击下钻和可访问性的维护成本较高。

备选二：全面迁移 React/Vue，适合更大的多页面产品，但这次会引入与目标无直接关系的迁移。当前不建议作为前置工作。

依赖通过构建产物随镜像提供，不使用在线 CDN。统计在后端算，前端负责展示；SQLite 为 Web UI 的长期分析来源，Grafana 继续使用 VictoriaMetrics。现有 VM 180 天保留期不应限制应用的同比分析。

参考：Flatpickr 官方[范围示例](https://flatpickr.js.org/examples/)与[多月选项](https://flatpickr.js.org/options/)；ECharts 官方[自定义系列](https://echarts.apache.org/handbook/en/how-to/custom-series/)、[拖动交互](https://echarts.apache.org/handbook/en/how-to/interaction/drag/)、[可访问性](https://echarts.apache.org/handbook/en/best-practices/aria/)。Context7 当前没有可用 API key，规划阶段以官方文档核对能力；实施锁版本时再次确认接口。

## 3. 信息架构与交互

### 3.1 页面层级

页面分为“健康趋势”“同步覆盖”两个主要视角，设置独立保留。

健康趋势：统一时间条 → 概览与周期变化 → 活动/步数 → 心率/压力 → 睡眠/恢复 → 训练负荷。用户点击图中某日打开详情抽屉，返回时保留范围、指标和焦点。

同步覆盖：年份/月份导航 → 完成比例与异常摘要 → 覆盖方块图 → 选中周期/日期详情 → 补缺或重试动作。原任务表移到详情抽屉，并提供分页、状态和类型筛选。

### 3.2 统一时间选择器

- 单个范围按钮，例如“近 30 天 · 08/29—09/27”；桌面弹出双月日历，移动端单月底部面板。
- 快捷选项：7 天、30 天、90 天、近一年、本周、上周、本月、上月、今年、去年、自定义。近期完整周期默认截止昨天，旁边提供“包含今天（进行中）”开关。
- 首页默认近 30 个完整自然日，避免今天尚未完成的数据压低趋势和比较。
- 日历支持连续范围高亮、快捷选年份/月份、明确的应用与取消、键盘操作和可编辑日期；不要求用户连续翻十几个月。
- 两侧“上一周期 / 下一周期”按钮平移范围；对本月等自然周期按自然周期移动，对 30 天等滚动区间按等长天数移动。
- 对比开关：关闭 / 上一周期 / 去年同期；显示实际比较日期，不能只写一个不透明的百分数。
- 应用时区统一；分析范围写入 URL，刷新和分享链接后可恢复。浏览器后退恢复先前范围。
- 选择状态区分草稿和已应用值，拖动或点选中途不发分析请求。
- 同步日历可以独立浏览年份；“查看这段健康趋势”显式同步到全局范围，单纯查看任务不能让健康页面突然跳日期。

### 3.3 多尺度同步日历

“年/月/周/日”定义为观察窗口，避免把年份、月份、日期混成不同含义的方块：

| 视角 | 显示内容 | 最小执行单元 |
| --- | --- | --- |
| 年 | GitHub 风格周列 × 星期行，每格一天；月份标签、年度完成比例，可前后切年 | 日期 × 接口 |
| 月 | 大尺寸月历，每格一天，显示完成数/应检查数和活动状态 | 日期 × 接口 |
| 周 | 7 天 × 数据类型矩阵，直接看哪天的哪类在等候或执行 | 日期 × 接口 |
| 日 | 当日各接口的执行条目，含最近成功、当前状态、重试次数、错误、数据情况、VM 待发送 | 日期 × 接口 |

顶部还可显示 12 个月的聚合完成条，帮助从年份定位月份。周跨年时保留真实日期，默认周一为一周开始。

主色编码：灰色未请求、蓝色排队、青色执行中、绿色已检查完成、琥珀色部分完成、红色失败。执行中的格子有轻微呼吸边框；混合周期可以显示黄色底 + 执行边框或失败角标，不让“运行中”覆盖已有失败提示。Token 失效显示全局暂停条及锁定图标，不将全部 pending 误判成正在执行。

颜色必须同时配图例、文字或图标。支持 `prefers-reduced-motion` 关闭动画；触屏点击可获取与桌面 hover 相同的信息。年图在窄屏提供可滚动周列或月份分页，周/月/日视角保留足够触控面积。

需要明确区分三种信息：

1. **采集任务**：成功检查了多少项，占预期项多少。未创建任务的日期也必须补入时间网格并显示灰色。
2. **测量覆盖**：成功响应是否包含数据、各指标有效点数/观测分钟；空响应展示空心标记和“已检查，暂无数据”，不能说设备不支持。
3. **输出状态**：本地归档完成但 VM 尚未投递、或有历史修订冲突，单独用徽标显示，不把成功采集改成失败。

父级完成率先汇总子级计数再做比率，不平均子级百分比。分母按当前计划采集的接口与区间内已到来的日期计算；未来日期禁用，不参与完成率。允许筛选单个接口查看进度。新增接口不能将旧版已完成任务历史悄悄改成成功，旧日新增项明确为“未检查”。

点格子查看详情；框选范围或使用按钮“补齐未完成 / 重试失败 / 强制刷新”。框选只是选择，不直接发请求；提交前显示日期和待执行数。任务仍落在现有持久队列，前端不维护第二套任务状态。

当某日已有成功归档，自动刷新重新排队时，要显示“已归档，等待刷新”，不能让历史完成覆盖看起来突然消失。新分析索引重算也有独立状态，不混入 Zepp 采集任务。

## 4. 趋势与统计口径

### 4.1 长期趋势是默认视图

| 主题 | 默认图表 | 下钻内容 |
| --- | --- | --- |
| 步数 | 每日柱图 + 7 日滚动均值；周/月可看合计与日均 | 当日活动片段及源数据覆盖 |
| 活动/运动 | 各类型时长堆叠柱、频率、总/日均时长、跑步距离；活动类型构成 | 类型列表、活动片段，已确认接口后的完整运动记录 |
| 心率 | 每日中位数/均值可切换，P25–P75 带；可选 P10–P90、静息心率独立系列 | 当日曲线、典型一天叠加、样本数和覆盖 |
| 压力 | 每日中位数/均值、分位带和滚动趋势 | 当日压力曲线，活动时段作为参照 |
| 睡眠 | 每夜实际可识别睡眠时长与阶段构成、作息时间、评分趋势 | 指定夜晚的阶段时间线及未识别区间 |
| 训练 | ATL/CTL/TSB、TRIMP、运动负荷趋势，分别保留单位和含义 | 选中日期数值与相关活动 |

图表默认只显示少量主要系列，其他统计由图例开关选择。百分位带表达样本分布，不标作置信区间，也不暗示医学正常范围。

30/90 天以日为单位，近一年仍可显示每日点；更长范围默认按周/月聚合，并明确粒度。统计来自完整有效样本，绘图降采样只发生在最后的显示环节，不能先降采样再算百分位。

### 4.2 典型一天与指定日叠加

用于心率、压力；横轴统一为应用时区的 00:00—24:00。

1. 各日先按 5 分钟时间桶归一化，桶内取中位数，每日每桶最多贡献一个值。
2. 同一时刻跨日计算 P50 主线、P25–P75 阴影；均值和 P10–P90 可切换。
3. Tooltip 给出“该时段基于 N 天”，避免穿戴更久的日期获得更多权重。
4. 日期滑块、前一天/后一天按钮和可搜索日期选择器控制一条高亮日曲线。拖动过程中仅加载邻近日缓存，不重算基线。
5. 基线范围固定为当前分析区间；切换叠加日不改变基线，叠加日默认也属于基线样本集，清楚说明这一点。
6. 缺失点断开，不插值造数据。某桶不足 5 个有效日时不画分位带，保留已知值和样本不足提示；至少两日才形成跨日统计线。
7. “工作日 / 周末”分组可作为后续开关；首版不追加大量筛选。

这里的“叠加”是基线带 + 指定日线，数值曲线不做相加堆叠。活动时长和睡眠阶段构成才使用堆叠图。

步数采用区间总量/日均及逐日趋势。由于当前只有日汇总及部分活动片段，不把片段内步数均匀摊成伪造的分钟级曲线。日内可展示已知活动块，未覆盖部分明确为空。

### 4.3 睡眠的专门处理

- 清醒、浅睡、深睡、REM 是分类，不能将数字编码平均后画“平均睡眠阶段”。
- 默认显示每夜阶段时长堆叠、已识别睡眠时长、睡眠记录跨度、评分与作息波动。
- “实际可识别睡眠时长”从不重叠的浅睡/深睡/REM 段汇总；缺段、重叠和未知阶段保留质量标识，不能将整段起止跨度自动当作全部睡眠。
- 入睡时间用跨午夜展开坐标计算，例如以中午为日界线，23:30 与 00:30 的中心应在午夜附近而非中午。
- 指定夜晚使用阶段时间线；若以后增加典型夜晚，采用“入睡后经过时间”的阶段占比分布，单列为后续增强，不与心率百分位逻辑混用。
- 当日运动/活动和当晚睡眠可联动查看，但不自动给出因果解释。

### 4.4 同比、环比与质量

- 滚动区间：环比为紧邻的等长完整区间；自然月/年提供上一月/上一年，清楚显示长度差异，默认以日均比较。
- 同比：按去年相同日历区间，闰日采用钳制到 2 月末的明确规则，并展示实际天数；本年至今与上年相同进度比较，不拿未完年度和完整年度比较。
- 若用户包含今天，今天标作进行中；默认比较只使用双方截至昨天的完整日期。界面显示分析范围与比较有效范围的差别。
- 同时显示差值、基期值和有效记录天数，例如“日均步数 +850，当前 27/30 天、对比 26/30 天”。
- 步数/活动比较提供总量和日均，缺失天不当 0；有缺日时总量不标成完整周期总量。
- 心率用 bpm 差、睡眠用分钟差、阶段比例用百分点差；只对有明确意义且基数为正的指标提供相对百分比。TSB 等可为负指标只显示绝对变化。
- 初版不把观测覆盖率直接当成佩戴时长；每天和每桶展示有效样本量与观测覆盖，用户可筛掉不完整日期。
- 比较有效日不足 7 天或不足所选区间 70% 时标注“低覆盖参考”，不隐藏现有数据；无对应历史显示“历史不足”，并可一键打开对应范围的回溯选择，用户确认后才执行。
- 有效日不足 7 天的短周期不产生“低覆盖”误报：最低日数取 `min(7, 区间总天数)`。质量阈值集中配置并在帮助中说明，属于显示策略，不是医疗判断。

## 5. 活动类型与运动记录的数据边界

第一阶段可从已有 band summary 提取：步行/跑步时长、跑步距离/热量、活动片段起止与 mode，以及片段步数、距离、热量。参考映射已知慢走、快走、跑步、轻活动；其他值显示“未知类型（原始代码）”，保留原始字段。

活动片段不是完整的训练记录；各类型只对已覆盖的片段汇总，不能强制让类型合计等于全天步数，也不把全天热量改称活动热量。

参考仓库文档有 `/v1/sport/run/history.json` 和 `/v1/sport/run/detail.json` 的运动列表与单次运动详情接口线索，但当前客户端没有完整实现。单列任务核实账号真实响应、分页、单位与 sport 类型枚举。确认后再接入骑行、游泳等类型及次数/距离/时长。无真实样例则交付已有类型与明确的待支持项，不虚构枚举和数据。GPS 路线、配速地图不属于本轮必需范围。接口线索来源：[上游 API reference](https://github.com/EvanCooke/zepp-export/blob/main/docs/api-reference.md)。

活动片段与完整运动记录同时存在时要保留来源；按覆盖时间/关联 ID 去重或分别展示，不相加重复计算活动总时长。

## 6. 数据与 API 设计

新增独立聚合层，保持现有采集与 VM 投递的事务语义。任务界面的数据类型按真实采集单元计数：例如 band 同时提供心率/睡眠/活动，只计一个采集任务，测量覆盖则可分别筛选健康维度。

- `zepp_report/analytics.py`：分位数、日/周/月趋势、日内基线、比较窗口、质量判断。分位数统一使用排序后线性插值 `h=(n-1)*p`，用固定样例验证。
- `zepp_report/coverage.py`：完整日期轴、状态聚合、测量覆盖、父级计数与状态优先级。
- `zepp_report/activity.py`：已知活动字段解析与来源区分。
- `zepp_report/analytics_store.py`、`migrations.py`：派生索引、版本与可恢复重算。
- 前端拆出 `range-picker.js`、`sync-calendar.js`、`trend-charts.js`、`day-inspector.js`、`api.js`、`state.js`，不再向一个大文件追加所有功能。

建议新增：

| 接口 | 职责 |
| --- | --- |
| `GET /api/coverage?from_date&to_date&view&kind` | 全范围状态格子、各类计数、测量覆盖、数据新鲜度、VM 状态 |
| `GET /api/tasks?from_date&to_date&status&kind&cursor` | 按需分页的任务明细，不再局限最近 30 条 |
| `GET /api/analytics/trends?from_date&to_date&metric&grain&compare` | 轻量趋势、质量和同比/环比窗口 |
| `GET /api/analytics/profile?from_date&to_date&metric&bucket_minutes=5` | 日内基线、分位带、各桶有效日数 |
| `GET /api/days/{date}` | 点击/滑动所选日的心率、压力、睡眠、活动明细 |
| `GET /api/activities?from_date&to_date&source&type` | 活动类型构成与按需列表 |
| `POST /api/sync/preview` | 给出选区待执行、已完成、失败数量，尚不创建任务 |
| 现有 `POST /api/sync` 与 `/api/retry` 扩展可选范围、类型 | 执行预览后的补缺/重试，默认语义保持不变 |

分析结果统一返回 timezone、grain、范围、有效样本数/日期数、quality、source_revision、algorithm_version。统计语义随响应明确，不让前端猜测。

派生数据按“日期 × 指标”保存日统计，并按“日期 × 指标 × 5 分钟桶”保存日内代表值；跨日分位数从这些每日代表值计算，不从已有分位数再合并成所谓全样本分位数。

以规范化内容哈希和算法版本标识变化，同样内容的重复采集不反复重算。采集事务提交时写入待重算标记和数据版本；单独的可恢复索引任务按日刷新派生表。首次升级优先生成近期 30 天，然后补历史；重启后继续。状态显示分析索引进度，已存在数据不可暂时显示成 0。旧版本缓存明确标作更新中，新接口可使用现有可用版本或等待，不能混合不同算法结果。

原始响应版本可重解析生成新增活动字段，不改写 raw_versions，不触发重复 VM 投递。派生表可删除后重建，但保留原始记录、任务和投递检查点；部署迁移只新增表/列与索引，使用版本化、可重复执行的迁移。

## 7. 分阶段执行清单

各任务均独立提交；后一阶段不要求前端读全量历史明细才能上线。

### 阶段一：时间选择与页面结构

## 8. 性能与可靠性验收

- 30/90/365天概览只返回聚合统计；365天心率请求不携带全年逐分钟样本。
- 热缓存的365天聚合 API 以本机代表性数据验证目标 P95 < 1 秒，年度任务网格 < 300 ms；统计这是工程目标，必须测量后报告，不提前承诺实测值。
- 年度状态网格响应目标 < 200KB；长历史以年度分片。日内曲线目标288桶/系列，样本数另带。
- 日期拖动视觉响应目标 < 100ms；联网查询节流约150ms并预取邻日，无重复请求风暴。
- 浏览器在375/768/1440px测试；键盘、触屏、色觉辅助、减弱动画、会话过期后恢复页面选择均覆盖。
- 数学用可手算样本验证：分位数、不同采样量等权、空值、睡眠跨午夜、负TSB、0基期、闰日、自然月长度不同。
- 恢复测试：同步时重启、分析重算时重启、Token 更新中断、VM失联、暂时磁盘失败、历史强制刷新后缓存失效。
- DST：日汇总按真实本地自然日；日内对齐按时钟标签，同一日重复时段合并为该日一个代表值，缺失时段留空并报告实际覆盖分母；不能假设每天总是1440分钟。
- `N/A`、空响应、未开始、未完成、确实为0分开，覆盖到UI与API。

## 9. 发布、回滚与边界

1. 用 SQLite 在线备份保留当前归档、任务及 Token 设置；测试库使用备份副本，测试不能重置线上用户配置。
2. 使用新镜像版本，执行旧库升级及恢复演练。现有41项基础测试保持通过，新增分析/日历/比较测试独立补充。
3. 沿用 stacks/AGENTS.md 的 homelab-v2、Traefik、无宿主机端口、bind mount 和 UID1000 设置；前端构建新增阶段随Docker镜像交付。
4. 数据库采用向后兼容的新增结构；默认回滚只切回旧镜像，不还原数据库，以免覆盖部署后的新增健康数据。确需恢复备份时先停服务并保留现库副本。
5. 原 Zepp 采集任务与 VM 投递语义保持；统计缓存和活动重解析不触发历史指标删除或无意重发。
6. Grafana 继续工作；本轮交互重点在 Web UI。新活动日汇总可在明确指标口径后补到 Grafana，不要求 Grafana 模仿所有复杂交互。
7. 不引入健康诊断、异常医学阈值或自动因果解释。所有统计以个人已观测数据为依据。

推荐执行顺序：阶段一 + 二先解决难操作和看不见进度；阶段三 + 四完成分析体验；阶段五将已证实的运动记录和整体版本发布收尾。每个阶段都有可演示增量，无需等所有高级分析完成才改进时间选择与回溯管理。
